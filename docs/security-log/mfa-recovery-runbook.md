# MFA 復旧手順（認証アプリ紛失時）

対象：管理者（company_members.role = admin）の認証アプリ（TOTP）を紛失した場合。
前提：管理者は MFA 登録が必須。登録済みの管理者は、操作時に AAL2（追加認証）が必要。

## 基本方針

- 本人確認なしに MFA の要素を解除しない。
- 解除は、Supabase プロジェクトのオーナーが行う（ダッシュボードの操作）。アプリに解除の画面・API は無い。
- 解除の前後の記録を、運用台帳に残す（アプリの監査ログには残らない）。
- MFA を一時的に無効化する設定変更や、ガードの回避はしない。
- service_role キーや JWT の値を、チャット・チケット・ログに貼らない。

## 手順 A：パスワードでログインできるが、認証アプリが無い

1. 本人から依頼を受け、本人確認をする（対面、または社内の登録済み連絡先への確認）。
2. 運用台帳に依頼日時、依頼者、対象の会社、対象のメールアドレスを記録する。
3. プロジェクトオーナーが Supabase ダッシュボードで、対象ユーザーの MFA 要素を削除する。
   - 画面の場所：Authentication → Users → 対象ユーザー → MFA（名称は画面により異なるため、要確認）。
4. 本人がパスワードでログインし、登録画面（/auth/mfa/enroll）で新しい認証アプリに再登録する。
   - 管理者は登録が完了するまで、管理操作（招待・権限変更・メンバー削除・全データ削除など）が 403 になる（`mfa_enrollment_required`）。
5. 再登録後、管理者画面の操作（例：メンバー一覧の表示）が成功することを、本人と確認する。
6. 運用台帳に、解除の完了日時と再登録の完了日時を記録する。

## 手順 B：プロジェクトのオーナーと管理者が同一人物で、認証アプリを失った

- 手順 A と同じく、プロジェクトのオーナーとしての Supabase ダッシュボードの操作で解除する。
- ダッシュボードへのログイン自体にも MFA を設定している場合は、Supabase のアカウント側の復旧手順に従う（Supabase のサポートへ問い合わせ）。

## 手順 C：管理者がパスワードも認証アプリも失った

1. プロジェクトオーナーがダッシュボードで、対象ユーザーのパスワードを再設定する（一時パスワードは、本人だけが受け取れる経路で渡す）。
2. 手順 A の 3〜6 を行う。
3. 一時パスワードは、次のログイン時に変更する。

## 管理者が他にいない場合

- 管理者が 1 人だけの状態は避ける。平時に、管理者を 2 人以上登録しておく。
- 全管理者を失った場合、Supabase ダッシュボードで管理者ロールを付与するには、DB の直接操作が必要になる。この操作は承認を得て、本番 DB で行う（手順は別途承認）。

## 技術的な代替手段（承認が必要）

- Supabase の管理 API には、要素を削除する関数がある（`auth.admin.mfa.deleteFactor({ id, userId })`）。
- 実行はサービスロールを使うため、承認を得た手順でのみ行い、実行は非本番で一度検証してから本番に適用する。
- 実行ログ（誰が、いつ、どの userId に対して行ったか）を運用台帳に残す。

## 禁止事項

- 本人確認なしの解除。
- 管理者の共有アカウントでの代理操作。
- MFA を無効化するためのコード変更や、ガードの一時的な除外。
- 解除を依頼された内容を、確認なしに実行すること。

## 復旧後の確認

- 管理者が登録画面で登録を完了し、AAL2 でログインできること。
- 管理者操作（例：メンバー一覧、招待作成）が成功すること。
- 運用台帳に、依頼・本人確認・解除・再登録の記録が揃っていること。

## 未確認事項

- Supabase ダッシュボードの MFA 要素の削除画面の正確な場所と名称（本番のダッシュボードで確認すること）。
- ダッシュボードの操作が、Supabase の監査ログに残るかどうか。
