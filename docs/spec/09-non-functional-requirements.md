# 09. 非機能要件（Non-Functional Requirements）

> 評価基準: **IPA「非機能要求グレード」**の 6 大項目（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境・エコロジー）。
> 各項目について **① 現状の実装事実（コード根拠）／② 外部クライアント PoC 向けの目標水準／③ ギャップと対応** を整理する。
> セキュリティ詳細は [08-security-review.md](./08-security-review.md) に委譲し、本書はサマリのみ。
> レビュー日: 2026-06-22（コード裏取り再監査: 2026-06-24）／ 対象: `growth-mvp` v0.2.0。

## 0. 前提（システム構成）

| 層 | 採用 | 特性 |
|---|---|---|
| フロント/API | Next.js 15（App Router）on **Vercel（サーバーレス）** | 自動スケール・従量課金・コールドスタートあり |
| DB/認証 | **Supabase（マネージド Postgres + Auth + RLS）** | 可用性は Supabase プランの SLA に依存 |
| AI | **OpenAI API（`gpt-4o` 系）** | 外部依存・レイテンシ/コスト/レート制限が外部要因 |
| クライアント状態 | Zustand `persist`（localStorage） | オフライン下書き保持・端末ローカル |

> 重要: 可用性・性能の多くが **外部マネージドサービスの SLA** に規定される。自社で作り込む余地は「冗長化」より「監視・上限・劣化時の振る舞い」に集中する。

## 1. 可用性（Availability）

### ① 現状
- Vercel / Supabase / OpenAI のマネージド可用性に依存。**自前の冗長化・フェイルオーバーは無し**。
- データ保全: 保存は楽観ロック（`revision`）＋直列化（`enqueueSave`）＋競合回復フロー（`strategyStore` に conflict/retry/revision 関連 約 62 箇所）。クライアントは localStorage 下書きで一時的なネットワーク断に耐える。
- **OpenAI 障害時の縮退（fallback）は実質なし**。`ask-ceo-agent` の `answerManual` は OpenAI 障害時の代替ではなく **操作ガイド（help/manual モード）用の追記ブロック**で、生成失敗時は本文が `'応答の取得に失敗しました。'` になるのみ（`route.ts:497` 付近）。
- タイムアウト: 一部の生成系（`generate-final-story` / `generate-story-draft` / `generate-advice` / `generate-department-question` / `stage2/generate-draft` / `stage2/generate-final` の 6 本）は **`AbortController` で 58 秒タイムアウト**を実装（`generate-final-story:682-704`）。**他の生成系・`ask-ceo-agent` には未実装**で挙動が不揃い。
- バックアップ手順・RTO/RPO の文書化は**未確認**。

### ② PoC 目標水準（最低限）

> 以下は **PoC の暫定目安**（硬い SLA 契約ではない。本運用ではクライアント要件で確定）。

- 稼働率: 数値 SLA は設けず**ベストエフォート**（目安として平日日中の重大停止ゼロ）。計画停止は事前通知。
- データ消失防止を最優先: **日次バックアップ有効＋リストア手順あり**。目安 **RPO 24h / RTO 4h**。
- OpenAI 障害時に**全機能が落ちない**（生成系のみ縮退、閲覧/入力は継続）。

### ③ ギャップ・対応
- [ ] Supabase 自動バックアップの有効化確認＋**リストア手順書**（[08] C-3）。
- [ ] OpenAI 障害時の**graceful degradation**を全生成系に統一（タイムアウトは 6 本のみ→全体へ、リトライ・「現在AI利用不可」表示の追加）。
- [ ] 死活監視（外形監視）と障害通知。

## 2. 性能・拡張性（Performance / Scalability）

### ① 現状
- スケール: Vercel サーバーレスで水平自動スケール。Supabase は接続数・プラン上限に従う。
- **性能目標値・負荷試験の記録は無し**。
- ボトルネック候補:
  - `strategy_data` が **1 会社 1 行の巨大 JSONB**。肥大化で保存/読込のペイロードが増大（`buildSavePayload`/`pruneUndefinedDeep` が毎回全体を処理。保存のたびに `JSON.stringify` で全体をシリアライズ）。
  - 生成系 API は OpenAI レイテンシ（数秒〜十数秒）に律速。モデルは `gpt-4o`（6 本）/ `gpt-4o-mini`（5 本）。`max_tokens` 指定は 12 ファイルにあり、応答長は部分的に上限制御されている。
  - **レート制限が無い**ため、スパイク時にコスト/接続が無制御（[08] F-3）。タイムアウトは一部生成系（6 本）のみ（§1）。

### ② PoC 目標水準（最低限）

> 以下は **PoC の暫定目安**（合否判定の当たりをつけるための値。本運用で実測・確定）。

- 通常画面（生成除く）: **p95 3 秒以内**を目安。
- 生成系 API: **タイムアウト 60 秒** + ローディング表示（現状 6 本に 58 秒。全生成系へ展開）。
- 同時利用: PoC 想定（**数社 × 数十ユーザー**）で破綻しない。
- 濫用・コスト暴騰の防止として**レート制限を入れる**（[08] F-3）。

> **同時編集の整合性（注意）**: 会社の `strategy_data` は 1 行・全文書保存のため、**複数ユーザーの同時編集で後勝ち（lost update）**が起こりうる（[01] §4.5）。編集ロールは admin/manager に限られるが、**全文書保存ゆえ別部門担当の manager 同士でも衝突する**（部門分担では防げない）。PoC では「**同じ会社の `strategy_data` を同時刻に編集する人を 1 人にする**」運用で回避し、恒久対応は §9 バックログ。

### ③ ギャップ・対応
- [ ] レート制限（IP/ユーザー単位）＋生成系の日次上限（[08] F-3）。
- [ ] `strategy_data` 肥大時の保存最適化（差分保存・分割の検討。現状は全体 upsert）。
- [ ] 代表シナリオでの**負荷試験**と p95 計測（フェーズ D）。

## 3. 運用・保守性（Operability / Maintainability）

### ① 現状
- **CI が無い**（`.github/workflows` 不在）。**自動テスト基盤も無し**（jest/vitest/playwright 不採用）。検証はスモークスクリプト（`scripts/stage3.smoke.mjs`、`rbac-check.sh`、`rbac-e2e-min.sh`）のみ。
- ビルドが**型/Lint エラーを無視**（`next.config.js` の `ignoreBuildErrors` / `ignoreDuringBuilds`＝[08] F-4）→ 退行を検知しにくい。
- ログ: `console.*` が多い（`store/strategyStore.ts` に 158、`app/api/**` 合計 437、`app/execution/page.tsx` に 69）。一部は `NEXT_PUBLIC_DEBUG_*` でガードされるが無条件出力も残る。**集中ログ/エラー監視（Sentry 等）は未導入**。
- 監査: [08] F-9 のとおり**永続監査ログが実質不在**。
- ドキュメント: 本 `docs/spec/` + 多数の調査/レポート（`docs/_md_dump/`, `docs/investigation/`）あり（厚い）。

### ② PoC 目標水準
- main への変更で **型チェック + Lint + スモーク**が自動実行される（CI 必須ゲート）。
- 本番エラーが**監視ツールに集約**され、即時アラートが飛ぶ。
- 重要操作（権限変更・削除・招待）が**監査ログで追跡可能**。

### ③ ギャップ・対応
- [ ] CI（`tsc --noEmit` / `next lint` / smoke / `rbac-e2e-min`）を構築し、`ignore*` を解除（[08] B-1）。
- [ ] エラー監視（Sentry 等）導入（[08] D-1）。
- [ ] `audit_logs` 新設（[08] F-9 / A-7）。
- [ ] ログのレベル制御・機微マスキング（[08] F-7）。
- [ ] 最低限の自動テスト（RBAC・保存/復元・主要 API）導入の検討。

## 4. 移行性（Migratability）

### ① 現状

- OKR は Phase 2A で `okrs` テーブルへ正本化、`strategy_data` スナップショットと二重化（移行途上）。バックフィル資料は `docs/dry-run/`。

### ③ ギャップ・対応

## 8. 参考資料の補足

非機能要件の「ものさし」も複数ある。目的・粒度で使い分ける（セキュリティ系の参考資料は [08] §14 を参照）。

| 参考資料 | 種類 | 特徴 |
|---|---|---|
| **IPA「非機能要求グレード」** | 国内標準の要求項目表 | 6 大項目（可用性/性能/運用保守/移行性/セキュリティ/システム環境）を**社会的影響度に応じたレベルで段階定義**。日本語・本書の骨格。要件合意・抜け漏れ確認に最適 |
| **クラウド Well-Architected Framework**（AWS/Google/Azure 等） | クラウド設計指針 | 信頼性・性能・コスト・運用・セキュリティの設計原則。**インフラ寄りの判断**に有用 |
| **SRE / SLO・エラーバジェットの考え方** | 運用指標の方法論 | 稼働率や遅延を**数値目標（SLO）として運用**する枠組み。本格運用フェーズで採用 |

### 違い
- **IPA 非機能要求グレード** = 「**何を・どの水準で要求するか**」の合意・棚卸し用（要件定義向き）。
- **Well-Architected** = 「**どう設計するか**」の指針（設計判断向き）。
- **SLO/SRE** = 「**運用後どう測り続けるか**」の方法論（運用向き）。

### 本 PoC の方針
1. **IPA 非機能要求グレードで現状と必要水準を棚卸し**（本書 §1〜§7 がそれ）。PoC は数値 SLA を置かず**最低限**（データ消失防止・濫用防止）に絞る。
2. 数値 SLO（稼働率・遅延の継続計測）や Well-Architected レビューは **本運用フェーズで採用**（PoC では過剰）。

## 9. あとでやれるといいリスト（PoC 後の改善バックログ・非機能観点）

PoC 最低ラインには含めないが、本運用・規模拡大で着手したい非機能項目。§1〜§6 の「PoC 前に必要な初期対応」は再掲せず、ここでは **初期対応後の継続運用・高度化** に絞る。セキュリティ寄りのバックログは [08] §15 を参照。

- [ ] **稼働率・遅延の SLO を定義し継続計測**（PoC は数値 SLA なし。本運用で SLI/SLO・エラーバジェットを設定）。
- [ ] **負荷試験を定例化**し、通常画面 p95・生成系レイテンシ・Supabase 接続数・OpenAI 呼び出し失敗率を継続観測。
- [ ] **`strategy_data`（巨大 JSONB）の差分保存・分割**で保存/読込を最適化（[09] §2）。
- [ ] **複数ユーザー同時編集の整合性向上**（フィールド単位保存／編集ロック・presence 表示／リアルタイム同期）。現状は全文書保存＋楽観ロックのため lost update のリスク（[01] §4.5）。
- [ ] **バックアップからの定期リストア訓練**を行い、RTO/RPO を実測して更新する（[09] §1）。
- [ ] **AI 縮退運用の高度化**（全生成系へのタイムアウト/代替表示適用後、失敗率監視・リトライ方針・モデル別 fallback を整備）。
- [ ] **監視運用の高度化**（外形監視の閾値、アラート通知先、一次対応手順、定期レビュー）。
- [ ] **OKR 二重ソースの正本一本化**（[09] §4、`docs/phase2a/`）。
- [ ] **対応ブラウザ/端末の最低要件を定期見直し**し、`browserslist`・サポートポリシー・動作確認範囲に反映。
- [ ] **自動テストと CI の拡充**（RBAC・保存/復元・主要 API から、E2E/回帰テスト・カバレッジ計測へ拡張）。
