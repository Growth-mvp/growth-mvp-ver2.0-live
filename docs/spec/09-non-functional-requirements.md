# 09. 非機能要件チェックリスト（Non-Functional Requirements）

本書は、**IPA「非機能要求グレード」の 6 大項目**（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）に沿って、PoC（2〜3 社への提供）前に満たすべき非機能要件を検証可能なチェックリストとして定めたものである。
セキュリティの詳細は [08 セキュリティ監査チェックリスト](./08-security-audit-checklist.md) に委譲し、本書は他 5 項目＋セキュリティのサマリを扱う。

- **対象システム**: `growth-mvp` v0.2.0（構成は §2）
- **策定日**: 2026-07-06（v2.0。初版 2026-06-22 の現状評価・コード裏取り 2026-06-24 の事実を「現状メモ」として引き継いだ）
- **数値の扱い**: 本書の数値（p95 3 秒・タイムアウト 60 秒・RPO 24h / RTO 4h 等）は **PoC の暫定目安であり、硬い SLA 契約ではない**。本運用移行時にクライアント要件で確定する。

## 2. 前提（システム構成）

| 層 | 採用 | 特性 |
|---|---|---|
| フロント/API | Next.js 15（App Router）on **Vercel（サーバーレス）** | 自動スケール・従量課金・コールドスタートあり |
| DB/認証 | **Supabase（マネージド Postgres + Auth + RLS）** | 可用性は Supabase プランの SLA に依存 |
| AI | **OpenAI API（`gpt-4o` 系）** | 外部依存・レイテンシ/コスト/レート制限が外部要因 |
| クライアント状態 | Zustand `persist`（localStorage） | オフライン下書き保持・端末ローカル |

> 重要: 可用性・性能の多くが**外部マネージドサービスの SLA** に規定される。自社で作り込む余地は「冗長化」より「監視・上限・劣化時の振る舞い」に集中する。

## 3. 要件項目一覧

> 「確認方法・合格基準」は実施担当者がそのまま作業に落とせる粒度で記載している。判定・証跡の各列は実施時（コピー先ファイル）に記入する。
> [08] の項目と重なる要件は検証を [08] 側に統合し、本書では要求水準の定義と参照のみを持つ（二重判定を避ける）。

### AV. 可用性（Availability）

> **現状メモ（2026-06-24 コード裏取り時点）**: Vercel / Supabase / OpenAI のマネージド可用性に依存し、自前の冗長化・フェイルオーバーは無し。データ保全は楽観ロック（`revision`）＋直列化（`enqueueSave`）＋競合回復フロー＋localStorage 下書き。生成系のタイムアウト（`AbortController` 58 秒）は 6 本のみ実装（`generate-final-story:682-704`）で、`ask-ceo-agent` 等は未実装。OpenAI 障害時の縮退は実質なし（`answerManual` は操作ガイド用であり障害時の代替ではない。失敗時は本文が「応答の取得に失敗しました。」になるのみ）。バックアップ手順・RTO/RPO の文書化は未確認。

| AV-02 | OpenAI 障害時に全機能が落ちないこと（graceful degradation） | OpenAI 呼出を強制失敗させ（無効キー等）、全生成系 API がタイムアウト（60 秒目安）とエラー表示で終了し、閲覧・入力・保存は継続できること。タイムアウト未実装の生成系ルートが残っていないことを grep（`AbortController`）で確認（PS-03 と連動） | 高 | ⬜ | |

### PS. 性能・拡張性（Performance / Scalability）

> **現状メモ（2026-06-24 時点）**: 性能目標値・負荷試験の記録なし。`strategy_data` が 1 会社 1 行の巨大 JSONB で、保存のたびに `buildSavePayload` / `pruneUndefinedDeep` が全体を処理し `JSON.stringify` で全体をシリアライズ。生成系は OpenAI レイテンシ（数秒〜十数秒）に律速（`gpt-4o` 6 本 / `gpt-4o-mini` 5 本、`max_tokens` 指定は 12 ファイル）。レート制限なし。
>
> **同時編集の注意**: `strategy_data` は 1 行・全文書保存のため、複数ユーザーの同時編集で**後勝ち（lost update）**が起こりうる（[01] §4.5）。全文書保存ゆえ**別部門担当の manager 同士でも衝突する**（部門分担では防げない）。恒久対応は §7 バックログ、PoC 中は PS-05 の運用回避で対処する。

| ID | 要件 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |
|---|---|---|---|---|---|
| PS-01 | レート制限とコスト上限があること | 検証は **[08] E-03 に統合**（同一要件）。IP / ユーザー単位のレート制限に加え、生成系の日次上限またはコスト上限の存在を確認 | **必須** | ⬜ | |
| PS-02 | 通常画面（生成除く）が p95 3 秒以内であること | 代表 5 画面（ログイン→ダッシュボード→Stage 表示等）で p95 を計測（ブラウザ DevTools / 負荷ツール）。超過する画面は原因と対応方針を記録 | 中 | ⬜ | |
| PS-03 | 全生成系 API にタイムアウトとローディング表示があること | 全生成系ルートにタイムアウト（60 秒目安。現状 58 秒×6 本）と、実行中表示・失敗時表示があることを grep＋実機で確認 | 高 | ⬜ | |
| PS-04 | PoC 想定規模で破綻しないこと | 想定規模（数社 × 数十ユーザー、同時 10〜20 リクエスト）の負荷試験を 1 回実施し、エラー率・p95・Supabase 接続数を記録 | 中 | ⬜ | |
| PS-05 | 同時編集の運用回避ルールが合意されていること | 「同じ会社の `strategy_data` を同時刻に編集する人を 1 人にする」運用が文書化され、PoC 企業へ説明済みであること（[08] H-05・M-02 と連動） | 高 | ⬜ | |

## 5. 参考資料の使い分け

非機能要件の「ものさし」も複数ある。目的・粒度で使い分ける（セキュリティ系の参考資料は [08] §4 を参照）。

| 参考資料 | 種類 | 特徴 |
|---|---|---|
| **IPA「非機能要求グレード」** | 国内標準の要求項目表 | 6 大項目を社会的影響度に応じたレベルで段階定義。日本語・本書の骨格。要件合意・抜け漏れ確認に最適 |
| **クラウド Well-Architected Framework**（AWS / Google / Azure 等) | クラウド設計指針 | 信頼性・性能・コスト・運用・セキュリティの設計原則。インフラ寄りの判断に有用 |
| **SRE / SLO・エラーバジェット** | 運用指標の方法論 | 稼働率や遅延を数値目標（SLO）として運用する枠組み。本格運用フェーズで採用 |

使い分けの軸:

- **IPA 非機能要求グレード** = 「何を・どの水準で要求するか」の合意・棚卸し用（要件定義向き）。
- **Well-Architected** = 「どう設計するか」の指針（設計判断向き）。
- **SLO / SRE** = 「運用後どう測り続けるか」の方法論（運用向き）。

本 PoC の方針: **IPA 非機能要求グレードで棚卸しし（本書 §3）、数値 SLA は置かず最低限（データ消失防止・濫用防止）に絞る**。数値 SLO の継続計測や Well-Architected レビューは本運用フェーズで採用する（PoC では過剰）。

## 7. PoC 後の改善バックログ（非機能観点）

PoC 最低ライン（§3 の項目）には含めないが、本運用・規模拡大で着手したい非機能項目。ここでは**初期対応後の継続運用・高度化**に絞る。セキュリティ寄りのバックログは `docs/security-log/` の第 1 回レビューを参照。

- [ ] **稼働率・遅延の SLO を定義し継続計測**（PoC は数値 SLA なし。本運用で SLI/SLO・エラーバジェットを設定）。
- [ ] **負荷試験を定例化**し、通常画面 p95・生成系レイテンシ・Supabase 接続数・OpenAI 呼び出し失敗率を継続観測（PS-04 の定常化）。
- [ ] **`strategy_data`（巨大 JSONB）の差分保存・分割**で保存/読込を最適化（現状は全体 upsert）。
- [ ] **複数ユーザー同時編集の整合性向上**（フィールド単位保存／編集ロック・presence 表示／リアルタイム同期）。現状は全文書保存＋楽観ロックのため lost update のリスク（[01] §4.5、PS-05 の恒久対応）。
- [ ] **バックアップからの定期リストア訓練**を行い、RTO / RPO を実測して更新する（AV-01 の定常化）。
- [ ] **AI 縮退運用の高度化**（AV-02 の適用後、失敗率監視・リトライ方針・モデル別 fallback を整備）。
- [ ] **監視運用の高度化**（外形監視の閾値、アラート通知先、一次対応手順、定期レビュー）。
- [ ] **OKR 二重ソースの正本一本化**（MG-03 の実行。`docs/phase2a/`）。
- [ ] **対応ブラウザ/端末の最低要件を定期見直し**し、`browserslist`・サポートポリシー・動作確認範囲に反映（EE-03 の定常化）。
- [ ] **自動テストと CI の拡充**（RBAC・保存/復元・主要 API から、E2E/回帰テスト・カバレッジ計測へ拡張）。
