## 1. 運用ルール

### 1.1 監査の実施タイミング

| タイミング | 実施範囲 |
|---|---|
| PoC 提供開始前 | 全項目（重要度「必須」は全件合格が提供条件） |
| 新企業（テナント）追加前 | カテゴリ B（セッション・会社選択）・D（テナント分離）・M（運用）を再実施 |
| 認証・認可・RLS・API に関わる変更のデプロイ前 | 該当カテゴリ（最低 A〜E） |
| 定期監査 | 四半期ごとに全項目 |
| 依存パッケージ更新時 | カテゴリ L |

### 1.2 判定基準

| 判定 | 意味 |
|---|---|
| ✅ OK | 合格基準を満たすことを証跡付きで確認した |
| ❌ NG | 合格基準を満たさない（是正タスクを起票し、備考にリンク） |
| ⚠️ 条件付 | 部分的に満たす／緩和策で暫定合格（期限付きで是正計画を記載） |
| ➖ N/A | 対象機能が存在しない等で該当しない（理由を記載） |
| ⬜ 未実施 | 未監査 |

### 1.3 重要度の定義

| 重要度 | 定義 | 是正期限の目安 |
|---|---|---|
| **必須** | 未対応のまま顧客データを預かれない（テナント越境・認証欠落・秘密鍵漏えい等） | **PoC 提供前に合格必須** |
| **高** | 悪用可能性が現実的で影響が大きい | PoC 期間の初期（2 週間以内） |
| **中** | 悪用条件が限定的、または影響が限定的 | 正式提供まで |
| **低** | 多層防御・品質向上として推奨 | 計画的に対応 |

> 「必須」項目の ⚠️ 条件付合格は、**文書化されたリスク受容（経営判断）がある場合に限り**認める（§5 の PoC 提供可否判定と対応）。

### 1.4 証跡の残し方

1. 監査実施時は本ファイルを**そのまま更新せず**、`docs/security-log/audits/YYYY-MM-DD_audit-NN.md` としてコピーし、判定・証跡・実施者・実施日を記入する（本ファイルはマスタとして維持。`docs/security-log/` は過去レビュー・是正証跡を含む追記専用のログ置き場で、レビュー一式は `review-NN/`、監査結果は `audits/` に格納する）。
2. 証跡は「コマンドと出力」「SQL と結果」「スクリーンショット」「対象コミット SHA」のいずれかを必ず含める。口頭・記憶ベースの「OK」は認めない。
3. 証跡には**検証時点のコミット SHA と日時**を記録する（コードが変われば証跡は失効するため）。
4. NG／条件付の項目は是正タスク（Issue 等）を起票し、次回監査で再検証する。
5. 実施のつど、**本マスタの §6（監査実施履歴）に 1 行だけ**追記する。判定・証跡の記入先はあくまでコピー先ファイルであり、**マスタへの記入はこの履歴 1 行のみを唯一の例外とする**（マスタを実施ログで汚さない）。
6. 前回監査の ❌ NG・⚠️ 条件付・持ち越しの ⬜ は、**次回監査ファイルの初期状態として引き継ぐ**（オープン項目を宙に浮かせない）。第 1 回の結果と状態は `docs/security-log/audits/2026-07-03_audit-01.md`（ベースライン）に集約済みであり、以後の是正状態は監査結果ファイルのみで管理する。

## 2. 監査項目一覧

> 「確認方法・合格基準」は監査担当者がそのまま作業に落とせる粒度で記載している。
> 判定・証跡の各列は監査実施時（コピー先ファイル）に記入する。実施日の列は持たず、**証跡欄に実施日時と対象コミット SHA を必ず含める**（§1.4-2/3 の証跡ルール）。

### A. 認証（Authentication）

対象: Supabase Auth（メール＋パスワード）、Bearer トークン検証、認証フロー画面群、招待トークン（[03] §1・§6）。

| ID | 監査項目 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |
|---|---|---|---|---|---|
| A-01 | 全 API ルートの認証要否が棚卸しされ、意図どおりであること | ルート総数は**監査時点で `find app/api -name route.ts` の件数として算出**する（固定値を持たない。参考: 2026-07 時点で 61 本）。全ルートを走査し「認証必須／不要／廃止済み」の分類表を作成。認証不要と分類されたルートは、その理由（招待受諾前・初回プロビジョニング等）が仕様として説明できること | **必須** | ⬜ | |
| A-02 | AI 生成系 API が無認証で呼べないこと | 未ログイン状態（Authorization ヘッダなし）で、A-01 の棚卸しで生成系に分類した全ルート（`generate-*`・`recommend-*`・`okr-from-exec`・`stage*/generate-*`・`ask-ceo-agent` 等）へ curl で POST し、**稼働中ルートは全件 401** を確認。**廃止済みルート（例: `generate-department-summary`・`knowledge` は 410 Gone）は 410 を返し、OpenAI 呼び出し・DB 書込等の副作用が無い**ことをコードで確認（OpenAI コスト悪用・DoS の防止） | **必須** | ⬜ | |
| A-03 | Bearer トークン検証が全保護ルートで統一実装であること | 保護対象ルートが**許可された認証ヘルパー**（`getAuthUserIdFromBearer()`、セッション系は `getAuthenticatedUserIdWithVerification()`）のいずれかを経由していることを grep で確認。許可ヘルパー以外の独自実装（トークン未検証・decode のみ等）が無いこと。個別実装を許容する場合は C-10 と同じ**理由つき許可リスト**で管理する | 高 | ⬜ | |
| A-04 | 期限切れ・改ざんトークンが拒否されること | 期限切れ JWT／署名不正 JWT／別プロジェクトの JWT で保護 API を呼び、401 を確認 | 高 | ⬜ | |
| A-05 | パスワードポリシーが設定されていること | Supabase Auth 設定（最小長・漏えいパスワード拒否）を確認。PoC 参加企業向けの推奨設定（8 文字以上等）を文書化 | 中 | ⬜ | |
| A-06 | サインアップが招待制で統制されていること | `/signup`・`/signup/admin`・`/signup-admin` の公開範囲を確認。任意の第三者がサインアップ→会社作成できる場合、PoC 運用（既知企業のみ）と矛盾しないかを判断。不要なら無効化またはアクセス制限 | 高 | ⬜ | |
| A-07 | `companies/provision` の悪用ができないこと | 認証済みの任意ユーザーが provision を繰り返し呼んだ場合の挙動を確認（会社の乱造・既存会社への membership 偽造・他人の profile 上書きができないこと） | **必須** | ⬜ | |
| A-08 | パスワード設定・再送フロー（`/auth/set-password`, `/auth/resend-set-password`）でアカウント乗っ取りができないこと | 他人のメールアドレスを指定した再送・設定リンクの推測・リンク再利用を試行し、いずれも不可であること | 高 | ⬜ | |
| A-09 | 認証コールバック（`/auth/callback`）にオープンリダイレクトが無いこと | `redirect_to` 等のパラメータに外部 URL を指定し、外部サイトへ遷移しないことを確認 | 中 | ⬜ | |
| A-10 | 招待トークンが期限切れ・再利用に対して安全であること | `company_invites.expires_at` 経過後のトークンで受諾できないこと、受諾済みトークンを再利用できないこと、トークンが十分なランダム性（32 byte）で生成されハッシュのみ DB 保存されることを確認（[03] §6。取消の運用面は M-04） | 高 | ⬜ | |
| A-11 | ログインへのブルートフォース対策があること | Supabase Auth のレート制限・ロックアウト設定を確認し、短時間の連続ログイン失敗（例: 20 回）で実際に制限が発動することを実機確認。CAPTCHA 導入の要否も評価 | 高 | ⬜ | |
| A-12 | admin ロールユーザーの MFA 方針が定まっていること | アプリ内 admin ユーザーに多要素認証（Supabase Auth の MFA）を課すか、課さない場合の代替統制（パスワード強度＋操作の監査）を文書化し PoC 企業と合意していること（L-04 の運営側ダッシュボード 2FA とは別の観点） | 中 | ⬜ | |

### B. セッション・Cookie

対象: `_session/set-company`・`_session/set-cookie`、会社選択 Cookie（[03] §2、[07]）。

| ID | 監査項目 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |
|---|---|---|---|---|---|
| B-01 | `_session/set-cookie` が無認証で任意 Cookie を設定できないこと | 未ログインで呼び出して拒否されること。認証済みでも設定可能な Cookie 名が許可リストで限定されていること（セッション固定化・Cookie 汚染の防止）。またクロスサイトからの POST（フォーム送信等）で Cookie 設定が成立しないこと（SameSite / Origin 検証） | **必須** | ⬜ | |
| B-02 | `_session/set-company` で所属外の会社を選択できないこと | 認証済みユーザーが自分の membership に無い `companyId` を指定して呼び、拒否されることを確認。かつ、この Cookie 値をサーバ側処理が信頼する箇所を全数特定し、いずれも membership 再検証をしていること。またクロスサイトからの POST による強制的な会社切替（CSRF）が成立しないこと | **必須** | ⬜ | |
| B-03 | セッション Cookie の属性が適切であること | `HttpOnly` / `Secure` / `SameSite`（Lax 以上）を実レスポンスヘッダで確認 | 高 | ⬜ | |
| B-04 | ログアウトでセッションが確実に失効すること | ログアウト後に旧トークン・旧 Cookie で API を呼び、401 を確認 | 中 | ⬜ | |
| B-05 | 会社切替時にクライアント状態が完全に初期化されること | `hardResetForCompanySwitch()` の対象に全ストア（strategyStore・userStore・questionStore・useAgentStore 等）と localStorage の persist 領域が含まれることをコードと実機で確認（前会社データの混入防止。[01] §4.5、[03] §2）。H-02（ログアウト時消去）と対で実施 | 高 | ⬜ | |

### C. 認可（RBAC・API ガード）

対象: `lib/rbac.ts` 権限マトリクス、`lib/server/rbacGuard.ts`、admin 系 API（[03] §3〜5、[07]）。

| ID | 監査項目 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |
|---|---|---|---|---|---|
| C-01 | 権限マトリクス（[03] §3.2）どおりに各ロールの API 実行可否が強制されること | admin / manager / member の 3 アカウントを用意し、代表的な書込 API（戦略生成・部門編集・メンバー管理・招待）を総当たりで実行。マトリクスと完全一致すること（`scripts/rbac-check.sh` / `rbac-e2e-min.sh` の活用可。ただしスクリプト自体の網羅性も確認対象） | **必須** | ⬜ | |
| C-02 | admin 限定 API が member / manager から呼べないこと | `admin/*`・`members`(DELETE/PATCH)・`members/role`・`invites/create`・`org-alignment/admin/*` を member / manager トークンで呼び、**全件 403** を確認 | **必須** | ⬜ | |
| C-03 | manager の部門スコープが API 側で強制されること | manager が**他部門**の `targetDeptId` を指定して部門編集系 API を呼び 403 になること。担当部門未設定の manager が安全側（不可）に倒れること（[03] §3.3） | 高 | ⬜ | |
| C-04 | `requireUserMatch` による本人一致検証が機能すること | 他人の `userId` を body に載せて本人限定 API（自分の OKR 更新等）を呼び、拒否されることを確認 | 高 | ⬜ | |
| C-05 | ロール昇格の経路が admin 経由のみであること | member / manager が自分自身または他人のロールを変更できる経路（`members/role` 以外の裏口: provision・invite accept・profiles 直接更新等）が無いことを確認 | **必須** | ⬜ | |
| C-06 | `getCapabilities(null)` が最小権限（member 相当）へフォールバックすること | 未所属・ロール不明時の挙動をユニットレベルで確認（[03] §3.2 注記） | 中 | ⬜ | |
| C-07 | UI の権限ガード（RoleGate / AdminGuard 等）がサーバ側検証の**代替になっていない**こと | UI 制御のみで守られている操作（対応するサーバ側強制が無いもの)を洗い出し、一覧化。各々について「RLS または API のどちらで最終強制されるか」を明記できること（[03] §5 の警告事項） | **必須** | ⬜ | |
| C-08 | 書込 API の防御順序（[03] §4）が標準どおり実装されていること | A-01 の棚卸し表を用いて**書込系ルートの全数**について、認証→membership→capability→スコープ検証の順に全段が存在することをコードレビューで確認。スコープ検証（`assertCompanyScopeByStrategyId` 等）の**呼び忘れ**が無いこと | **必須** | ⬜ | |
| C-09 | 最後の admin を降格・削除できないこと | 会社の admin が 1 人の状態でロール変更（`members/role`）・メンバー削除を試行し、拒否されることを確認（テナントのロックアウト防止。旧08 G-3 の維持確認） | 高 | ⬜ | |
| C-10 | 認可被覆の CI ゲートが存在すること | 全書込ルートに認証・認可ガードの存在を機械検査する CI が構成され、未ガード検出でビルドが失敗すること。pre-auth 設計のルート（`companies/provision`・`invites/complete` 等）は**理由つき許可リスト**で管理されていること（C-08 の全数レビューの退行防止。旧08 F-5／旧08b A-3） | **必須** | ⬜ | |

### D. マルチテナント分離・RLS

対象: 会社単位のデータ分離、RLS ポリシー、Service Role の利用（[02] §1、[03] §2・§7）。
**本システムは `strategy_data`・`okrs`・`progress_logs` へクライアントから anon キーで直接書き込むため、RLS がテナント分離と書込権限の最終防衛線である（[02] §1.1 ★、[03] §5 警告）。本カテゴリは最重要。**

| ID | 監査項目 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |
|---|---|---|---|---|---|
| D-01 | 全テーブルの RLS 有効化状態が棚卸しされていること | `select relname, relrowsecurity from pg_class` 等で全テーブルの RLS 有効/無効を一覧化。クライアントから参照されるテーブル（[02] §1 の一覧）はすべて有効であること | **必須** | ⬜ | |
| D-02 | コア 6 テーブル（companies / company_members / profiles / strategy_data / okrs / progress_logs）の RLS ポリシー定義が文書化・検証されていること | `pg_policies` を introspect し、各テーブルの SELECT / INSERT / UPDATE / DELETE ポリシーを証跡として保存。[02] §1.1 の「RLS 未確認」状態を解消すること | **必須** | ⬜ | |
| D-03 | 会社 A のユーザーが会社 B のデータを**読めない**こと（クロステナント READ） | 2 社 2 ユーザーを用意し、B 社の `company_id` / `strategy_id` を指定して anon キー＋A 社ユーザーの JWT で `strategy_data`・`okrs`・`progress_logs`・`org_alignment_*`・`company_members` を SELECT。**全件 0 行**であること | **必須** | ⬜ | |
| D-04 | 会社 A のユーザーが会社 B のデータを**書けない**こと（クロステナント WRITE） | 同上の構成で B 社レコードへの UPDATE / INSERT / DELETE を試行し、全件拒否されること | **必須** | ⬜ | |
| D-05 | member ロールが戦略データを書き換えられないこと（ロール条件付き RLS） | member の JWT で自社の `strategy_data` を UPDATE、自社の `okrs` を INSERT/UPDATE し、**拒否**されること。RLS が「会社一致」だけでなく「ロール条件」まで見ていることの実地確認（[03] §5: UI 判定はバイパス可能） | **必須** | ⬜ | |
| D-06 | manager の部門スコープ逸脱書込が RLS または API で止まること | manager の JWT で他部門相当のデータ更新を直接 SQL（PostgREST 経由）で試行し、防御層（RLS／API のどちらか）で確実に止まることを確認。止まらない場合は既知リスクとして NG 判定 | 高 | ⬜ | |
| D-07 | Service Role キー利用 API のスコープ検証が全数漏れなく行われていること | `getSupabaseAdmin()` を使用する全ルートを grep で列挙し、各々が membership 検証＋会社スコープ検証（`assertCompanyScopeByStrategyId` / `resolveCompanyIdFromStrategyId` 等）を行っていることを表にして確認。**Service Role は RLS を素通しするため、検証漏れ 1 本がテナント越境になる** | **必須** | ⬜ | |
| D-08 | API への ID 差し替え攻撃（IDOR）が防がれること | 認証済み A 社ユーザーとして、リクエスト body / query の `companyId`・`strategyId`・`departmentId`・`caseId` 等を B 社の値に差し替えて主要 API を呼び、全件 403/404 であること（生成系・org-alignment 系・admin 系を含む） | **必須** | ⬜ | |
| D-09 | `agent_logs` の読み取りがユーザー間で分離されていること | agent_logs はアプリ内 select 無しの書込専用（[01] §4.5）だが、anon キーで直接 SELECT した場合に他人・他社の会話ログが読めないことを RLS で確認 | 高 | ⬜ | |
| D-10 | 招待テーブル `company_invites` の RLS が有効で、他社の招待・token_hash が読めないこと | 他社ユーザー・無所属ユーザーの JWT で SELECT し 0 行を確認 | 高 | ⬜ | |
| D-11 | コアスキーマが migration として正本化され、環境間ドリフトが無いこと | 本番スキーマの dump と `supabase/migrations/` の差分を確認（[02] §1.1 の #1 課題）。RLS ポリシーが migration 管理外で手動変更されていると、再構築時に**分離が黙って消える**リスクがあるため必須扱い | **必須** | ⬜ | |

### E. API セキュリティ（入力検証・出力・レート制御)

対象: `app/api/` 全ルート共通の堅牢性（本数は A-01 で監査時点に算出。[07]）。

| ID | 監査項目 | 確認方法・合格基準 | 重要度 | 判定 | 証跡 |

### 4.1 参考資料の使い分け

セキュリティの「チェックシート」は複数あり、**目的・粒度・言語・合否判定に使えるか**が異なる。混同せず、用途で使い分ける。

| 参考資料 | 種類 | 特徴 | 言語 |
|---|---|---|---|
| **OWASP Top 10** | リスクの地図 | 代表的リスク 10 カテゴリ。全体像把握・教育向け。**合否判定には粒度が粗い** | 日/英 |
| **OWASP ASVS**（Application Security Verification Standard） | 検証要件チェックリスト | 認証/アクセス制御/入力検証/ログ等を**合否式**で網羅。L1(基本)/L2(標準)/L3(高セキュア)の段階あり | 主に英 |
| **OWASP WSTG**（Web Security Testing Guide） | テスト手順書 | 実際に攻撃を試す**動的テストの how-to** | 英 |
| **OWASP Cheat Sheet Series** | 実装の手引き | CSP・JWT・Cookie 等、**個別対策の辞書** | 英 |
| **IPA「安全なウェブサイトの作り方」** | 国内教育＋対策 | 代表的脆弱性 11 種＋対策＋失敗例。**日本語・国内文脈で読みやすい**。ASVS ほど網羅/合否式ではない | 日 |
| **IPA「ウェブ健康診断仕様」** | 簡易診断項目 | 軽量なチェック項目。簡易点検・動的テストの項目出しに | 日 |
| **Supabase Production Checklist / RLS ガイド** | スタック固有（データ層） | RLS・認証・バックアップを公式が項目化。**本書 D カテゴリ（テナント分離）に直撃** | 英 |
| **Vercel Production Checklist / Security・Firewall** | スタック固有（基盤層） | DDoS/WAF・レート制限・環境変数・Deployment Protection。**E-03・G カテゴリ・L-05/L-08 に効く** | 英 |
| **Next.js「Going to Production」** | スタック固有（アプリ層） | セキュリティヘッダ・キャッシュ・ビルドの本番前チェック。**E-08・L-07 に効く** | 英 |
| **OWASP Top 10 for LLM Applications** | AI/LLM 固有リスク | Prompt Injection 等 LLM アプリの代表リスク。**F カテゴリに直結** | 英 |
| **OWASP ML Security Top 10 / NIST AI RMF / MITRE ATLAS** | AI セキュリティ標準 | ML/AI への攻撃と管理策の枠組み。AI 機能の設計・運用指針 | 英 |

選び方の軸:

- **目的**: リスク地図（Top 10）／検証要件（ASVS）／テスト手順（WSTG）／実装辞書（Cheat Sheet）／国内教育（IPA 作り方）／簡易診断（IPA 健康診断）／スタック固有（Supabase・Vercel・Next.js）。
- **合否判定に使えるか**: ASVS・IPA 健康診断・各スタックチェックリストは項目チェック向き。Top 10・IPA 作り方は教育・網羅確認向き。
- **言語**: 社内・国内クライアント説明は IPA（日本語）、客観的証跡は ASVS（国際標準）。

### 4.2 スタック固有チェックリスト（3 層）

本プロダクトは Supabase + Vercel + Next.js 構成のため、公式チェックリストを**役割の異なる 3 層**として併用する。

| 層 | チェックリスト | 主に効くカテゴリ |
|---|---|---|
| データ層（DB・認可・RLS） | **Supabase** Production / RLS | D（テナント分離＝最重要）・J |
| 基盤層（公開・WAF・秘密情報・レート制限） | **Vercel** Production / Security・Firewall | G・E-03・B・L-04/L-05/L-08 |
| アプリ層（ヘッダ・キャッシュ・ビルド） | **Next.js** Going to Production | E-08・L-07・H |

### 4.3 本監査での使い分け方針

1. **データ保護は Supabase Production/RLS チェックリスト**で潰す（D カテゴリ＝最重要）。
2. **基盤（公開・WAF・レート制限・環境変数）は Vercel チェックリスト**で確認（E-03・G カテゴリ・L-08）。
3. **アプリ（セキュリティヘッダ等）は Next.js Going to Production**で確認（E-08・L-07）。
4. **全体の合否基準は OWASP ASVS Level 1 相当**（PoC は L1 で十分。本書の項目はこの水準を目安に設計している）。
5. **国内向け説明・教育は IPA「安全なウェブサイトの作り方」**。
6. **動的テストは OWASP WSTG / IPA 健康診断**の項目を使う。
7. 個別実装の修正時は **OWASP Cheat Sheet** を辞書として参照。
8. **AI/LLM 機能は OWASP Top 10 for LLM Applications** を基準に対策（F カテゴリ）。

> 使い分けの目安: 「**スタック 3 層（Supabase=データ / Vercel=基盤 / Next.js=アプリ）＋ ASVS L1=合否表 / IPA=国内説明 / WSTG=実機テスト / OWASP LLM Top10=AI**」。
