# revision トリガー本番反映チェックリスト

対象: `public.strategy_data` への `bump_strategy_data_revision` トリガー追加と、STAGE3 再生成方式・保存競合対策を含む新アプリの反映。
SQL: `scripts/sql/release/revision-trigger/`（`01_precheck.sql` → `02_add_trigger.sql` → `03_postcheck.sql`、切り戻しは `04_rollback.sql`）。

**このチェックリストは手順の確定のみです。本番での実行は、下記の承認を得てから行います。**

## 0. 前提と残存リスク（必ず読む）

- 利用者には、保存・ログアウト・タブ終了を依頼します。作業終了は運用で確認します。
- **既に開いている旧タブは止められません。** 旧タブの古い JS による上書きは、トリガー追加後も完全には防げません（`departments`、`stage4Plans` などが旧タブの値で残る）。
- 書き込み停止は技術的に保証されません。JWT の失効待ちや、セッションの強制失効は採用しません。
- 新アプリは `revision` が進むことを前提にしています。トリガーが無いまま新アプリを出すと、初回保存後に保存が止まります。**トリガーを先に確認してから、新アプリをデプロイしてください。**

## 4. STAGE2〜4 の確認（検証用データ）

**共通の合格条件**: 保存後に `revision` が増加すること。自動保存で 1 回の操作につき複数回増えることがあるため、「+1」ではなく「増えた」で判定する。

**共通の記録方法**: 検証用会社の `company_id` を控え、SQL エディタで読み取りのみ行う。

```sql
select revision,
       jsonb_array_length(departments) as dept_count
from strategy_data
where company_id = '<検証用company_id>';
```

以下の各項目の前に `revision` を読み（R0）、操作後にもう一度読み（R1）、R1 > R0 を確認する。

**STAGE2**
- [ ] 回答を 1 件保存し、`revision` が増えた。リロード後も回答が残っている。
- [ ] 最終ストーリーを生成・保存し、`revision` が増えた。
- [ ] 競合: タブ A・B で同じ戦略を開く。A で保存した後、B で保存する。B に競合の表示が出て、B の保存が止まる。DB の `revision` は A の保存の値のままで、B の内容で上書きされていない。

**STAGE3**
- [ ] 候補の生成: 既存の計画（`dept_count` と計画の内容）が変わっていない。候補は保存されないため、生成の前後で `revision` が変わらない。
- [ ] 候補の選択追加: 候補のプロジェクトを 1 件採用する。`departments` にそのプロジェクトのタイトルが入り（`jsonb_path_exists(departments, '$[*].projects[*] ? (@.title == "<採用したタイトル>")')` が true）、`revision` が増えた。
- [ ] 部門戦略の項目別反映: 部門提案の項目を 1 つ反映する。反映した項目の値が変わり、`revision` が増えた。「反映しない」を選んだ項目は変わっていない。
- [ ] 既存の橋渡しがある場合、再生成の前に確認が出る。

**STAGE3 → STAGE4 の維持**
- [ ] STAGE3 で採用したプロジェクトを、STAGE4 で実行計画を編集して保存する。保存後も、採用したプロジェクトが `departments` に残っており（上記の `jsonb_path_exists` が true）、`revision` が増えた。

**STAGE4**
- [ ] 実行計画・人的投資を 1 件保存し、リロード後も残っている。`revision` が増えた。
- [ ] 競合時の未保存編集の保護: タブ A・B で同じプロジェクトを開く。A で同じ項目（例: 計画の状態）を変えて保存する。B で同じ項目を別の値に変えて保存すると、保存が止まって競合が表示される。B の未保存の編集は画面に残っており、DB には書き込まれていない（DB の値は A の保存のまま）。
- [ ] 別々のプロジェクトを、A と B がそれぞれ変えて保存する。両方の変更が残る（同じプロジェクトを両方が変えた場合は、項目が違っても競合になる）。

## 6. 切り戻し

**原則**: アプリを先に戻し、DB は後で戻す。トリガーは残すのが基本です。

1. **新アプリに問題がある場合**: 旧アプリ（`origin/main`）をデプロイする。トリガーは残したままにする。旧アプリはトリガーがあっても動く（`revision` が進むだけ）。
2. **トリガーも戻す必要がある場合**: 必ず旧アプリのデプロイが済んでから、`04_rollback.sql` を実行する。
   - 逆順（トリガーを先に外す）は危険です。新アプリが `revision_anomaly` で保存を止めます（データは消えないが、保存できなくなる）。
   - 新アプリのタブが開いている間は、トリガーを外さない。
3. `04_rollback.sql` は `trg_strategy_data_bump_revision` だけを削除します。関数と他のトリガーは残ります（検証済み）。
4. 切り戻し後は、旧タブの上書きリスクが戻ることを利用者と責任者に共有する。
5. 切り戻しも `DB_CHANGE_HISTORY.md` に追記する。
