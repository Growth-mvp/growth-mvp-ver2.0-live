# revision トリガー本番反映チェックリスト

対象: `public.strategy_data` への `bump_strategy_data_revision` トリガー追加と、STAGE3 再生成方式・保存競合対策を含む新アプリの反映。
SQL: `scripts/sql/release/revision-trigger/`（`01_precheck.sql` → `02_add_trigger.sql` → `03_postcheck.sql`、切り戻しは `04_rollback.sql`）。

**このチェックリストは手順の確定のみです。本番での実行は、下記の承認を得てから行います。**

## 0. 前提と残存リスク（必ず読む）

- 利用者には、保存・ログアウト・タブ終了を依頼します。作業終了は運用で確認します。
- **既に開いている旧タブは止められません。** 旧タブの古い JS による上書きは、トリガー追加後も完全には防げません（`departments`、`stage4Plans` などが旧タブの値で残る）。
- 書き込み停止は技術的に保証されません。JWT の失効待ちや、セッションの強制失効は採用しません。
- 新アプリは `revision` が進むことを前提にしています。トリガーが無いまま新アプリを出すと、初回保存後に保存が止まります。**トリガーを先に確認してから、新アプリをデプロイしてください。**

## 6. 切り戻し

**原則**: アプリを先に戻し、DB は後で戻す。トリガーは残すのが基本です。

1. **新アプリに問題がある場合**: 旧アプリ（`origin/main`）をデプロイする。トリガーは残したままにする。旧アプリはトリガーがあっても動く（`revision` が進むだけ）。
2. **トリガーも戻す必要がある場合**: 必ず旧アプリのデプロイが済んでから、`04_rollback.sql` を実行する。
   - 逆順（トリガーを先に外す）は危険です。新アプリが `revision_anomaly` で保存を止めます（データは消えないが、保存できなくなる）。
   - 新アプリのタブが開いている間は、トリガーを外さない。
3. `04_rollback.sql` は `trg_strategy_data_bump_revision` だけを削除します。関数と他のトリガーは残ります（検証済み）。
4. 切り戻し後は、旧タブの上書きリスクが戻ることを利用者と責任者に共有する。
5. 切り戻しも `DB_CHANGE_HISTORY.md` に追記する。

## 7. 承認が必要な操作

1. 作業終了の運用確認を前提に、リリースを進めること。
2. 本番での `01`〜`03` の実行。
3. 検証用会社データへの本番書き込み（`revision` の確認）。
4. 新アプリのデプロイ。
5. push（リリースに必要な場合のみ）。
