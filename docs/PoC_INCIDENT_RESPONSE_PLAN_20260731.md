**版番**: v1.0

**有効期間**: PoC期間中

## 重要な注記

本文書は、**センターボード社内で使用する参考資料・対応メモ**です。

- 本文書は、PoC提供先企業への提出を前提としません
- 正式なSLAや24時間対応を約束する文書ではありません
- 実際のインシデント対応は、PoC契約・覚書および先方企業との合意内容を優先します
- 本文書に記載の対応時間、対応体制等は、PoC開始前に先方企業と合意した内容のみが有効です

## 1. 目的と範囲

本計画書は、GROWTH SHIFT PoC提供中に障害、情報漏えい、不正アクセス等のインシデントが発生した場合の対応手順を定めるものです。

**対象**:
- PoC対象企業から報告されたセキュリティ事象
- GROWTH SHIFT プラットフォーム内で検知された異常動作
- 外部サービス（OpenAI、Supabase、Vercel等）の障害に起因する問題

**対象外**:
- PoC対象企業側のシステム障害
- インターネット接続障害

| 重大度 | 区分 | 例 |

## 5. インシデント検知・事実確認フロー

### 5.1 検知経路

インシデントは以下のいずれかで検知されます：

1. **PoC提供先企業からの報告**
   - メール / 電話で当社窓口に連絡
   
2. **当社監視システムからの検知**
   - Supabase エラーアラート
   - Vercel デプロイ障害アラート
   - OpenAI API 異常検知
   - 監査ログ異常（不正アクセスの疑い）


### 5.2 初期対応（報告から30分以内）

**段階1: 受領確認**

```
当社窓口
  ↓
事象の受領を確認
  ↓
詳細情報の聴取
  - 発生日時
  - 影響範囲（ユーザー数、データ量等）
  - 既実施の対応
  - 重大度の初期判定
  ↓
PoC担当責任者へ一報
```

**段階2: 事実確認**

```
当社技術対応窓口
  ↓
GROWTH SHIFT システムの確認
  - ログ（audit_logs, agent_logs）の確認
  - DB（Supabase）の接続性確認
  - API エラーの確認
  - 外部サービス（OpenAI等）のステータス確認
  ↓
原因の初期仮説を立てる
  ↓
重大度を確定（P0-P3）
```

### 5.3 重大度別初期対応時間（要確定）

以下は参考値（目安）です。実際の対応時間は、PoC開始前に先方企業と合意した内容を優先します。

| 重大度 | 初期報告 | 原因特定開始 | 復旧予定 |
|--------|---------|-------------|---------|
| P0 | 目安 30分以内 | 目安 1時間以内 | 要確定 |
| P1 | 目安 1時間以内 | 目安 2時間以内 | 要確定 |

| P3 | 目安 翌営業日 | 目安 翌営業日 | 要確定 |

**注**: 各対応時間は当社が実際に対応可能で、PoC提供先企業と合意した内容に限定する。PoC開始前に確定すること。

## 6. 利用停止・アクセス遮断等の初動対応

### 6.1 P0 インシデント時の対応

**情報漏えい確認時**:
1. 当該企業のアカウントを一時停止
2. 他の PoC 対象企業への波及リスク評価
3. PoC 提供先企業へ直ちに報告

**不正アクセス確認時**:
1. 当該ユーザーのセッションを強制削除
2. 当該企業の API キー / トークンを無効化
3. PoC 提供先企業へ直ちに報告
4. 当社側でアクセス制御を実施

**システム停止時**:
1. 本番 PoC 環境を停止
2. PoC 提供先企業への通知（メール + 電話）

### 6.2 P1-P3 インシデント時の対応

- PoC 提供先企業に状況を通知
- 復旧予定時刻を回答
- 進捗を定期報告（30分～1時間ごと）

### 8.1 調査対象

| 調査対象 | 確認項目 |
|---------|---------|
| **GROWTH SHIFT ログ** | audit_logs, agent_logs の異常記録 |
| **Supabase** | DB接続エラー、RLS ポリシー実行エラー、quota 超過 |
| **Vercel** | デプロイ成功/失敗、ランタイムエラー、Function 実行ログ |
| **OpenAI** | API レスポンス時間、エラーコード、rate limit 状況 |
| **ネットワーク** | DNS 解決、API 疎通確認 |

### 8.2 調査手順

```
1. PoC 提供先企業から詳細情報を追加聴取

4. ネットワーク疎通確認

6. 原因を特定・ドキュメント化
```

## 11. 情報漏えいまたは漏えい疑いがある場合の対応

### 11.1 検知時の対応（即座）

```
1. 当該企業のアカウントを一時停止
2. 漏えい範囲の特定
   - 対象ユーザー数
   - 対象データ（個人情報、入力データ等）
   - 漏えい経路
3. PoC 提供先企業へ一報（電話）
4. 当社内で情報セキュリティ責任者に報告
```

### 11.2 事実確認（30分以内）

```
1. audit_logs, agent_logs で不正アクセスの有無を確認
2. Supabase 監査ログで異常なアクセスを確認
3. 漏えい日時の特定
4. 流出した可能性のあるデータを一覧化
```

### 11.3 PoC 提供先企業への報告（1時間以内）

**報告内容**:
- 漏えい日時
- 流出したデータ内容（具体的に）
- 流出範囲（どのユーザーが対象か）
- 当社の対応措置
- 今後の対応予定

### 11.4 個人データ漏えい時の対応

**報告対象の確認**:
漏えいしたデータが「個人情報」に該当するか確認し、個人情報保護法による対応が必要か判定。

**個人情報に該当する場合の対応**:

1. **個人情報保護委員会への報告**
   - **速報**: 概ね 3～5日以内に報告
   - **確報**: 30日以内（不正目的のおそれがある場合は 60日以内）に詳細を報告

2. **本人への通知**
   - 速やかに影響を受けた本人に通知
   - 通知内容: 漏えいの事実、対象データ、対応措置

3. **PoC 提供先企業への報告**
   - 上記と並行して、PoC 提供先企業にも報告

**注**: 個人情報該当性の判断が不確定な場合は、安全側（保護委員会報告が必要と判定）に対応する。

## 12. 外部サービス障害時の対応

### 12.1 Supabase（データベース）障害時

**検知**:
- DB 接続エラー → API で 5xx エラー発生
- Supabase ステータスページで公開されている障害

**初期対応**:
1. Supabase ステータスページを確認
2. 公式ステータスから復旧予定時刻を確認
3. PoC 提供先企業に状況を報告（予定時刻を含む）
4. リトライ待機

**復旧確認**:
- SELECT クエリで DB 応答確認
- PoC 提供先企業に復旧報告

### 12.2 Vercel（ホスティング）障害時

**検知**:
- デプロイ失敗
- 関数実行エラー
- 時間外アクセス不可

**初期対応**:
1. Vercel ステータスページ確認
2. デプロイ履歴確認（最後のデプロイが成功しているか）
3. PoC 提供先企業に状況報告

**その他の対応**:
- PoC 提供先企業に状況を報告
- 復旧予定時刻を確認

### 12.3 OpenAI API 障害時

**検知**:
- AI 生成 API（/api/generate 等）で timeout / 5xx エラー
- OpenAI ステータスページで公開状況

**初期対応**:
1. OpenAI ステータスページ確認
2. API レスポンス時間を計測
3. PoC 提供先企業にリトライ方法を案内

**代替手段**:
- 生成機能一時停止の検討
- 代替回答（テンプレート等）の提供

### 12.4 Upstash Redis（レート制限）障害時

**検知**:
- レート制限が機能していない（リクエスト制限が解除される）
- Upstash ステータスページで障害報告

**対応**:
1. 当社システムの状態を確認
2. **対象API（生成系、招待系）を一時停止または制限側に制御**
3. PoC 提供先企業に状況を報告

**注**: 単なる周知ではなく、無制限開放を避けるため、必要に応じて該当 API を停止または安全側（制限側）に制御する。

### 12.5 その他外部サービス

| サービス | 障害時の対応 |
|---------|----------|
| **Resend（メール配信）** | メール遅延の可能性を PoC 企業に通知 |
