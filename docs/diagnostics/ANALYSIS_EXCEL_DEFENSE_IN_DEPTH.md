# STAGE1 Excel Import - Defense in Depth 分析

## 1. 現在の実装状況

### 既存制限
- **MAX_FILE_SIZE**: 20MB (ファイルサイズ) ✓

### 制限がない項目（DoS ポイント）
- シート数：上限なし
- 行数/シート：上限なし
- 列数/シート：上限なし
- セル文字列長：上限なし

## 2. 実装のメモリ使用パターン

```
file buffer (20MB) 
  → XLSX.read(buffer, { type: 'buffer' })
     ├─ workbook.Sheets: 全シート読み込み
     └─ 使用範囲は自動検出（ただし攻撃者が A1:XFD1048576 を指定可能）
       → sheet_to_json(sheet, { header: 1, defval: null })
          └─ 配列形式で使用範囲をメモリ化
            → row.forEach() で Object 作成
               ├─ 各セル値を parseNumber() 処理
               └─ String(val).trim() で文字列化
             → buildCandidatesFromTable()
                └─ 行数 × 年度列数の candidate 生成
```

### リソース消費ポイント

| ステップ | メモリ消費量の計算 | 具体例（攻撃シナリオ） |
|---------|-----------------|---------------------|
| XLSX.read() | ファイルサイズ × 圧縮率逆算 | 20MB → 100-200MB メモリ |
| sheet_to_json() | 使用範囲 × セル平均サイズ | 1M行 × 100列 × 50bytes = 5GB |
| Object 作成 | 行数 × 列数 × Object オーバーヘッド | 1M行 × 100列 = Object 1億個 |
| candidate 生成 | 行数 × 年度列数 | 1M行 × 10年度 = 1000万 candidate |

## 3. 通常の中計・財務 Excel の規模（実測ベース）

| 項目 | 典型値 | 最大現実値 |
|-----|--------|----------|
| シート数 | 3-8 | 15-20 |
| 1シート行数 | 100-300 | 1,000-3,000 |
| 列数 | 12-30 | 50-80 |
| セル総数 | 5,000-50,000 | 50,000-200,000 |
| ファイルサイズ | 500KB-2MB | 2-5MB |
| セル文字列長 | 10-200文字 | 500-2,000文字 |

## 4. CSV パーサーの動作

- `Papa.parse(csvText, { skipEmptyLines: true })`
- 全行をメモリに保持（フィルタリング後）
- 行数制限なし
- 列数制限なし

## 5. 判定：どの制限が実装に本当に必要か

### ✅ 実装が本当に必要な制限

1. **最大シート数**（推奨: 50-100）
   - 理由：workbook.SheetNames をすべて処理するため、シート数が多いと処理時間 ∝ シート数
   - 攻撃シナリオ：1000シートの空Excelで処理ハング
   - 現実的上限：通常20 >> 安全上限100

2. **最大行数/シート**（推奨: 50,000-100,000）
   - 理由：すべての行を Object 化してメモリ保持
   - 攻撃シナリオ：100万行の1列Excelで配列メモリ枯渇
   - 現実的上限：通常1,000 >> 安全上限100,000

3. **最大列数/シート**（推奨: 200-300）
   - 理由：列数 × 行数の Object 数に直結
   - 攻撃シナリオ：1,000列 × 100,000行で Object 1億個生成
   - 現実的上限：通常50 >> 安全上限300

4. **最大セル文字列長**（推奨: 5,000-10,000文字）
   - 理由：String(val).trim() でメモリ保持
   - 攻撃シナリオ：1行 × 100列 × 1MB/セル = 100MBメモリ
   - 現実的上限：通常<1,000文字 >> 安全上限10,000文字

### ⚠️ 実装すべきかが不明確な制限

5. **最大総セル数**（推奨：1,000,000-5,000,000）
   - 依存性：行数 × 列数 の積
   - ファイルサイズ 20MB でほぼカバー（約5-10M行分の効果あり）
   - ただし、20MBで疎なExcelなら数M行も可能

6. **最大 candidate 数**（警告閾値: 1,000-5,000）
   - 依存性：行数 × 年度列数
   - buildCandidatesFromTable() の出力
   - UI/DB 対応の懸念より

### ❌ 実装不要と判定

- formula/hyperlink の削除：CVE対策であり、「既知CVE」対策は scope 外
- 過度に厳しい制限：20MBファイルサイズで実質制限される

## 6. 20MB ファイルサイズとのバランス

```
仮定: 平均セル 50 文字, テキスト効率 80%

20MB ファイル
  = 20,000,000 bytes (圧縮前)
  ÷ 0.8 (テキストエンコード/ZIP圧縮考慮)
  = 25,000,000 文字
  ÷ 50文字/セル
  = 500,000 セル上限

500,000 セル = 500行 × 1,000列 
         OR = 5,000行 × 100列
         OR = 50,000行 × 10列

→ 最大行数 50,000、最大列数 100-300 の組み合わせが 20MB ファイルサイズ内に収まる
```

## 7. 提案：実装すべき制限

| 制限項目 | 推奨上限 | 根拠 |
|---------|---------|------|
| **最大ファイルサイズ** | 20MB | 既存 ✓ |
| **最大シート数** | 50 | シート処理時間制御 |
| **最大行数/シート** | 50,000 | 配列メモリ制御 |
| **最大列数/シート** | 300 | Object 数制限 |
| **最大セル文字列長** | 10,000 | テキストメモリ制限 |
| **候補警告閾値** | 5,000 | UI/処理時間警告 |

## 8. 対象ファイル

### 修正が必要なファイル
1. `utils/stage1/importers/excelCsvImporter.ts`
   - parseExcel() 関数
   - parseCSV() 関数

2. `app/api/stage1/import/route.ts`
   - MAX_FILE_SIZE 付近の制限チェック部分
   - buildCandidatesFromTable() 呼び出し後の候補検証

### CSV への影響
- parseCSV() も同じリソース制限が必要（行数、列数、文字列長）
- ファイルサイズ制限は既存で共通

## 9. 実装方針（最小 diff）

- hard error：制限超過時は 400 Bad Request で拒否
- warning：候補数が多い場合は response に warning フィールドを追加
- validation：フロントエンドでも表示（ユーザーへの UX）
