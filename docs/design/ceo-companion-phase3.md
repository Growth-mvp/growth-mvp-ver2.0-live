# AI経営コンサルタント PHASE 3 設計（STAGE5・6の経営点検）

## 1. 目的と範囲

STAGE5（実行）とSTAGE6（業績・資金）の保存済みデータから、経営上の気づきを自発的に示す。

- 実行の遅延・停滞（KRの期限超過、進行中のまま更新がない実施事項）
- 計画と実績の乖離（売上効果の計画比）
- 経営目標の未達リスク（施策反映後の見通しと目標の差）
- 資金不足リスク（施策・借入反映後の期末現預金と最低現預金の差）
- 原因の仮説、改善策・見直しの候補、部門横断の論点（AIが書く）

範囲外：STAGE0〜6の画面・DB・RLS・共通store・保存処理・財務計算ロジックの変更。AIによる戦略・計画・実績データの変更。

## 2. 基本方針

1. **事実はプログラムで決める。** 数値は既存の計算結果（資金繰り試算、見通し、計画と実績の照合、KRの実績、実施事項の進捗）をそのまま使う。
2. **AIは事実を説明するだけ。** 事実が無ければAIを呼ばない。AIに渡すのは事実の文だけで、数値を作らせない。
3. **事実と仮説を分ける。** 表示は「事実」の節を先に出し、AIの所見は「仮説」「見直しの候補」「部門横断の論点」の節に限る。
4. **AIが止まっても事実は出る。** AIの失敗時は事実だけを表示し、所見が取得できなかったことを明記する。
5. **呼び出しは会社ごとに1日1回。** 同じ日に再読み込みしても依頼しない。同じ内容の再依頼はしない（表示の文は保存し、再読み込み後に読む）。
6. **重大なリスクを進行の案内より優先する（PHASE 4）。** 資金不足・経営目標の未達（重大）は、進行の案内が残っていても経営点検を前に出し、進行の案内を隠す。それ以外（重大でない事実）は、進行の案内が出ていない時だけ出す。

## 3. 事実の規則

しきい値と判定は `lib/companion/companionRisk.ts` の `detectRiskFacts` に集約する（純粋関数）。

| 区分 | 事実にする条件 | 数値の出所 |
|---|---|---|
| CASH（資金不足） | 予測年度で、施策・借入反映後の不足額が0より大きい | `cashflow` の `postShortfall`（`outlookOf` の `financedPlan`） |
| TARGET（目標未達） | 経営目標との差（施策反映後）が不足（正の値） | `outlook.unifiedPl.gap` |
| PLAN_GAP（計画と実績） | 売上効果で、照合が完了し、登録実績が計画の80%未満 | `planActualYearRowsOf`（`REVENUE` モード）。費用の項目は対象外（後述） |
| KR_OVERDUE（期限超過のKR） | 期限（YYYY-MM-DD または YYYY-MM の末日）を過ぎ、実績が未登録、または目標に届いていない | KRの `due` / `target` / `actual`。低い方が良い指標（CHURN・COST_FIXED・COST_VARIABLE）は逆向きに判定する |
| ACTION_STALLED（停滞） | 進行中（IN_PROGRESS）で、更新日時から30日以上経っている実施事項 | `progressOf` の `status` と `updatedAt` |

- 事実の件数は最大8件（`MAX_FACTS`）。超えた分は表示しない。
- 事実の並びは上の区分の順。同じ内容なら同じ指紋になる。
- 保存データの読み込みに失敗した時、対象の会社の保存状態が判定できない時は、その区分の事実を作らない（未入力と断定しない）。

## 4. 処理の流れ

```
どの画面でも、伴走ON・保存済み・未保存なし・会社ごと今日未依頼 のとき（PHASE 4 で画面の制限を外した）
      └ POST /api/companion/risk-review（認証・会社の所属を確認）
          ├ 保存済みの戦略データを読み、事実を作る（既存の計算のみ）
          ├ 事実が0件 → AIを呼ばず {facts: [], text: null}（案内は出さない）
          └ 事実がある → AI（処理設定 ceoRiskReview）に事実だけを渡し、所見を得る
              → {facts, text}。監査ログに件数と AI使用の有無を残す
  └ 画面：「事実（保存済みデータの計算結果）」→ 所見（AI、失敗時は説明文）
  └ 本文は、このタブ（sessionStorage）に保存し、再読み込みでも再依頼せず表示する
```

## 6. 安全設計

- 自動変更なし。案内・所見は表示のみ。
- AI呼び出しは「事実がある」「会社ごと1日1回」の時だけ。
- 応答に失敗しても再依頼しない（同じ日は再び依頼しない）。
- 会社・利用者ごとに記録を分ける。会社切替で表示中の所見を消し、切替前の応答は表示も保存もしない。
- 権限：読み取りのみ。所属していない会社の戦略データは読まない（`requireMembership`）。
- AIへの規則：事実の数値を変えない、仮説と明記する、操作手順を書かない、判断は利用者に委ねる、600字以内。

## 7. 既知の制限（残課題）

- **費用の項目の計画と実績は対象外。** 費用の乖離は、符号と計算の基準を確認してから加える。
- **会社全体の目標（STAGE2）のKRは対象外。** 部門・プロジェクトのKRのみ。
- **停滞は更新日時だけで判定する。** 実施事項の期限（開始予定日）は持っていないため、「遅れ」とは断定せず「更新がない」と示す。
- **KRの向き** は指標の種類で決めている。種類が増えた時は `LOWER_IS_BETTER` を更新する。
- **実データでの事実は0件。** 実ブラウザの確認は、点検APIをモックして行った（第9章）。実データの事実が出る状態での所見の確認は、検証用データが必要。
- **AIの所見の品質** は、事実の文に対する規則の遵守で担保する。数値の逸脱を機械的に検査する仕組みは無い。

## 9. PHASE 4：最終検証（2026-11-19）

### 9.1 表示の優先順位

| 状態 | 表示 |
|---|---|
| 重大な事実（資金不足・目標未達）あり | 経営点検を前に出し、進行の案内は隠す（進行の案内は次の機会に出る） |
| 重大でない事実のみ | 進行の案内が出ている間は出さない。進行の案内が出ていない時に出す |
| 事実なし | AIを呼ばず、何も出さない |
| 点検APIの失敗 | 何も出さない。進行の案内は残る |
| AIの所見の失敗 | 事実だけを出し、「AIの所見は取得できませんでした」と明記する |

### 9.2 発話頻度

- 経営点検：会社ごと1日1回（点検APIは1回。AIは事実がある時だけ1回）。
- 進行の案内：案内ごとに1日1回、1セッション最大3件、表示の間隔60秒。
- 節目の助言：節目ごとに1回、1日2件まで。

### 9.3 回答の長さ（実際のOpenAI応答、2件）

| 事実の組み合わせ | 字数 | 構成 |
|---|---|---|
| 重大（資金不足・目標未達・期限超過・停滞） | 577字 | 仮説・見直しの候補・部門横断の論点（3節） |
| 重大でない（計画との乖離・停滞） | 475字 | 同上 |

いずれも600字以内。数値は事実の文のものだけで、新しい数値は作られなかった。操作手順は含まれなかった。一方で「未登録のため判断できない」の表現が、点検していない項目にも使われることがあった（改善の余地。判断材料が無いことは正しく示す）。

### 9.4 表示の分かりやすさ（実ブラウザ、モック）

- 経営点検の本文は「事実（保存済みデータの計算結果）」→ 所見（仮説・見直しの候補・部門横断の論点）→「点検していない範囲」の順。
- 点検していない範囲は必ず末尾に出る（費用の計画と実績、会社全体のKR）。

### 9.5 実ブラウザでの確認（モック）

| 項目 | 結果 |
|---|---|
| 重大なリスクが進行の案内より前に出る | 確認（進行の案内は隠れる） |
| 同じ日に再読み込み | 保存した所見を表示。点検APIは増えない |
| 重大でないリスク | 進行の案内を優先。点検は出ない |
| 点検APIの失敗 | 進行の案内は残る |
| AIの所見の失敗 | 事実のみ表示。失敗の文言を表示 |
| 点検していない範囲の表示 | 確認 |

### 9.6 確認できなかった項目

- **会社切替（実ブラウザ）**：アプリ内で会社を切り替える操作がなく、アカウントも1社のため実施できず。Jestで、処理中の助言が切替後に表示・保存されないことを確認（`components/CEOChatPanel.companion.test.tsx`）。
- **助言APIの失敗（実ブラウザ）**：節目の助言を発生させるには保存データの変更が必要なため実施できず。Jestで、失敗時に再依頼せず案内も出さないことを確認。
- 上記2点は、検証用の会社（本番DBの変更を伴わないもの）が用意できた時に実施する。

### 9.7 費用の乖離（対象外）

- 費用（OPEX・コスト削減・追加費用）の計画と実績は点検していない。経営点検の本文に、その旨を必ず添える。
- 会社全体のKR（経営目標）の進捗も点検していない（同じ注記に含む）。

### 9.8 既存機能への影響と本番ビルド

- Jest：全体で487スイート成功（8スイートは既存のスキップ）、6262件成功。
- 型チェック：95件（導入前の基準と同じ）。変更したファイルにエラーなし。
- 本番ビルド（`npm run build`）：成功。`/api/companion/risk-review` を動的ルートとして含む。
- STAGE0〜6、DB、RLS、共通store、保存処理、財務計算ロジックは変更していない（既存関数の公開のみ：`storedOf`、`outlookOf`）。
