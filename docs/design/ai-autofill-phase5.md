# AI自動入力・操作代行 設計（PHASE 5）

## 1. 目的

利用者がAI経営コンサルタントに依頼するだけで、GROWTH SHIFTの入力が進む仕組みを作る。
ただし、AIには任意のコードやAPIを実行させない。AIの役割は、依頼の意図の読み取りと説明に限り、
入力の中身は公開資料から決定的に取得し、利用者の承認後に既存の入力処理で反映する。

## 4. 安全設計

- **承認前は反映しない。** 候補取得はストアを変えない。反映は「承認して反映」の押下時のみ、`setProfile` を1回呼ぶ。
- **既存データを無断で上書きしない。** 入力済みの項目は、利用者が「上書きする」を選んだ時だけ反映する。
- **企業ID・戦略ID・権限を、取得時と反映時の両方で確認する。** 取得時はサーバーで所属・役割・戦略の対応を確認。反映時は画面の企業と戦略が取得時と同じかを確認し、違えば反映しない。
- **AIに任意のAPIを実行させない。** 公開資料の取得先は EDINET の提出書類一覧に固定。AIは関与しない。
- **DB・RLS・共通store・保存処理・財務計算は変更しない。** 反映は既存の `setProfile` のみ。保存は既存の自動保存が行う。
- **出典・決算年度・連結・単位の検証。** 候補ごとに、書類ID・提出書類の種類・期末日・決算年度を持つ。書類に無い「連結・単体」と「通貨の単位」は、推測せず「未確認」と示す。
- **取得できない項目は未入力のまま。** 証券コードの形式が違う、期末が読めない、提出者名が無い場合は、その項目を候補にしない。
- **停止手段。** 環境変数 `NEXT_PUBLIC_STAGE1_AUTOFILL_DISABLED=true` で、画面の部品を非表示にし、サーバーは 503 を返す。
- **外部への問い合わせは1回ずつ。** 429 などの失敗では再試行しない（期間の途中で止める）。
- **監査。** 候補取得は、会社・利用者・書類ID・期間・件数を監査ログに残す。

## 5. EDINET の取得（未確認事項）

- 提出書類一覧 API（`https://api.edinet-fsa.go.jp/api/v2/documents.json?date=YYYY-MM-DD&type=2&Subscription-Key=…`）を前提にしている。
  **API キーでの実呼び出しは未確認。** 応答の項目名（`docID`、`secCode`、`filerName`、`docTypeCode`、`periodEnd`、`withdrawalStatus`）も、実応答で確認が必要。
- 証券コードでの検索は、日付単位の一覧を範囲で読んで探す。範囲は31日以内。有価証券報告書の提出時期（決算後）を、利用者が指定する必要がある。
- 必要な準備：環境変数 `EDINET_API_KEY`（未設定。`.env.local` には作っていない。秘密値はリポジトリに入れない）。

## 6. 検証状況

- 単体試験：候補の生成（証券コードの変換、出典、決算月、未確認の表示）、反映の計画（承認、既存値の保護、上書き）、EDINET の読み取り（1回のみ、429で止まる、範囲の制限、書類の選び方）。
- 入口の試験：停止、認証なし、入力不正、所属なし、member の拒否、戦略と会社の不一致、鍵なし、成功、該当なし、429。
- 画面の試験：候補表示でストアが変わらない、承認で反映、取得後の企業切替で反映しない、入力済みの会社名は上書きしない。
- **未実施**：実 EDINET での取得（日本製罐など）、実ブラウザでの入力反映（検証用の会社が必要。本番DBへのテスト書き込みはしない方針）。

## 7. 残課題（5B・次の段階）

1. **EDINET の API キーの用意と、実データでの取得精度の検証**（日本製罐を対象に、候補の値と有価証券報告書の記載を照合する）。
2. **5B：過去5年間のPL・BS の候補**。EDINET の XBRL（または CSV）の解析が必要。単位（百万円・千円）、連結・単体、年度の対応を、書類ごとに検証してから候補にする。解析の検証には実データが必要。
3. **自然言語での依頼**：CEOチャットの依頼を、固定の操作（候補取得）に対応づける。AIは証券コードと期間を抽出するだけとし、取得と反映はプログラムが行う。
4. **既存の `externalFinancialSearch` は未使用のまま**（呼び出し元はコメントアウト）。本機能では使わない。
