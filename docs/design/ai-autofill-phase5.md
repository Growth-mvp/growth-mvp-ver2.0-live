# AI自動入力・操作代行 設計（PHASE 5：5A 仕上げ・5B）

## 1. 目的と入口

AI経営コンサルタントへの自然言語の依頼（例：「日本製罐の基本情報を入力して」「証券コード5905の財務データを取り込んで」）を入口に、
公開資料（EDINET の有価証券報告書の構造化データ）から基本情報と5期の財務を候補にし、
利用者の承認後に既存の入力処理で反映する。AIは依頼の読み取りに使わず（判定は決定的）、数値の取得と照合はプログラムが行う。
手動入力は従来どおり残す。

## 2. 実装範囲と状況

| 項目 | 状況 |

| 業種 | 実装済み（5C）。EDINET提出者業種を、業種区分へ対応表で対応（対応できないものは未入力） |

## 4. 提出日の範囲（システムが決める）

- 上場企業の有価証券報告書は、決算月に応じて提出時期が集中する（3月決算は6月、12月決算は3月、1月決算は4月、など）。
- 会社の決算月は特定の前は分からないため、提出が集中する月を優先順に読む：6月、3月、4月、9月、12月、7月、10月、1月、2月、5月、8月、11月。
  各月は直近の該当期間のみ。今日より後は読まない。土日は読まない。1日1回。
- 有価証券報告書が見つかったら、その提出後45日の範囲で、同じ期の訂正報告書（書類種別 130）を確認してから止める。
- 読み取りの上限：150日（超えたら途中で止め、証券コードでの指定を求める）。
- 実測（2026-11-19、実データ）：日本製罐は54日（6月の窓で発見）、丹青社は99日（6月・3月は見つからず、4月で発見）。

## 6. 確認事項（厳格に）

- **決算年度**：期末日から年度を決め、候補ごとに持つ。
- **連結・単体**：主要指標と連結財務諸表の照合で確定。従業員数は書類の要素だけでは連結・単体を確定できないため「未確認」。
- **通貨・単位**：CSV の単位が「円」の値だけ採用。「円」でない値は除外して、その旨を示す。
- **訂正報告書**：同じ期の訂正報告書がある時は、その値を採用し、元の書類との関係を示す。
- **取得できない項目**：推測で補わない。未取得の項目は、承認欄と反映結果に明示する。

## 7. 安全設計

- **承認前は反映しない。** 候補の取得・チャットの依頼では、入力欄（ストア）を変えない。反映は「承認して反映」の押下時のみ。
- **既存データを無断で上書きしない。** 入力済みの項目・年度は、利用者が上書きを選んだ時だけ変える。
- **企業ID・戦略ID・権限。** 取得時にサーバーで所属・役割（manager以上）・戦略と会社の対応を確認。反映時に画面の企業と戦略が取得時と同じかを確認し、違えば反映しない。
- **AIに任意のコードやAPIを実行させない。** 公開資料の取得先は EDINET に固定。AIは依頼の入口でのみ使い、数値には関与しない（現行の判定は AI を使わない）。
- **DB・RLS・共通store・保存処理・財務計算は変更しない。** 反映は既存の setter（`setProfile` `setFinancePL` `setFinanceBS`）のみ。保存は既存の自動保存。
- **停止手段。** `NEXT_PUBLIC_STAGE1_AUTOFILL_DISABLED=true` で、承認欄を隠し、依頼の入口も 503 を返す。
- **APIキーの扱い。** 鍵は環境変数 `EDINET_API_KEY` にのみ置き、応答・ログ・画面に出さない（ログは状態コードのみ）。
- **外部への問い合わせ。** 429 などの失敗では再試行しない。読み取りの上限を設ける。
- **監査。** 候補の作成は、会社・利用者・書類ID・読み取った日数を監査ログに残す（本番の監査テーブルへの書き込み。試験では監査は模擬している）。

- 抽出：日本製罐・丹青社の実データ（最小の行だけ抜き出した試験データ）で、上表の値・照合結果・単位・照合不一致の扱い。
- 特定：依頼文の解析、窓の順序、平日のみ、上限、曖昧な会社名、訂正報告書の確認。
- 候補と反映：出典・連結区分、業種・セグメントの未取得、入力済みの保護、年度ごとの上書き、同じ値の扱い。

- 入口（API）：停止、認証、入力不正、所属・役割・戦略の不一致、依頼の不明、鍵なし、特定の結果（曖昧・未発見・上限）、成功、訂正の採用、取得失敗（再試行しない）。
- 画面：候補の取得で入力が変わらない、承認で反映、入力済みの保護、企業切替で反映しない、曖昧な会社名の表示、チャットからの候補。

1. ～5C（10章）で対応済み。残りは10.10の制限を参照。

## 10. PHASE 5C（仕上げ：企業特定の効率化・財務5期・セグメント・一気通貫）

### 10.1 企業の特定（EDINETコードリスト）

- 金融庁のEDINETコードリスト（`https://disclosure2dl.edinet-fsa.go.jp/searchdocument/codelist/Edinetcode.zip`、Shift_JIS）を使う。提出者11,468件（上場・非上場）、証券コード・提出者業種・決算日・所在地を含む。
- 会社名・証券コードの検索は、この一覧で行う（書類の走査はしない）。一覧は24時間だけ保持し、並行の取得は1回にまとめる。取得に失敗した時は保持しない。
- JPXの東証上場銘柄一覧は使わない（この一覧に証券コードと業種が揃っているため、追加の取得が不要）。
- 同名の会社が複数あれば推測せず候補の一覧を返す（例：「東洋」→ 東洋紡、東洋水産、東洋製罐グループHD）。

### 10.2 業種（EDINET提出者業種 → STAGE1の業種区分）

- 東証33業種の名称を、STAGE1の選択可能な16区分に対応させる（対応表は `lib/autofill/industryMap.ts`）。例：金属製品→製造業、サービス業→その他サービス業、情報・通信業→情報通信・IT。
- 対応表に無い名称は業種を埋めず、未対応として示す。対応は業種名だけで決め、数値からは推測しない。

### 10.3 決算期ごとの有価証券報告書（提出日の範囲はシステムが決める）

- 決算日から期の終わりを作り、その後92日以内の平日を新しい日から読む（締切近くに提出が集中するため）。
- 提出後45日の範囲で、同じ会社・同じ期の訂正報告書（130）を確認する。訂正があれば訂正の構造化データを採用し、元の書類との関係を示す。
- 日付ごとの提出書類（有価証券報告書と訂正だけ）は24時間保持する。失敗は保持しない。
- 直近5期のために、直近の期と2年前・4年前の期の3つの報告書を読む（2年前の報告書は2期分、4年前の報告書は2期分の損益を持つため）。

### 10.4 5期の統合（値の選び方と食い違い）

- 年度ごとの値は、その年度の報告書の値を基本にする（丸めの精度が高い）。
- 後の書類の値が、その年度の値と100万円（百万円単位の丸め）を超えて違う時は、修正（再表示）とみなし、新しい書類の値を採用して注意に残す。
- 100万円以内の差は丸めとみなし、注意にしない。
- 営業利益は、報告書の連結財務諸表にある2期（前期・当期）だけ。3つの報告書で5期分を取る。取れなかった年度は0で埋めず、未取得のままにする。
- 決算期の月日が報告書ごとに違う時は、決算期の変更の可能性として注意に残す（2年おきの取得は正常）。

### 10.5 事業情報（セグメント）

- 報告セグメントごとの売上高・営業利益（連結）を、連結の財務諸表の文脈から取る。セグメントの合計（報告セグメント）が全体と一致することを確認する（差は100万円以内を許容）。
- セグメントの名前は、説明文（報告セグメントの概要）の「〜事業」の並びから取り、件数が報告セグメントの数と一致した時だけ、順番どおりに対応付ける（要確認と注記）。一致しなければ名前は付けず、区分コードのまま未入力。
- 事業内容は、本文の「事業の内容」を取り込む（2,000字まで）。

### 10.6 反映と取り違えの防止

- 承認欄は、企業名・証券コード・所在地・業種・従業員数・事業内容・決算月・上場区分・年度ごとの財務・事業セグメントを、項目ごとに出典つきで示す。
- 登録中の企業（会社名・証券コード）と取得対象が違う時は、「異なることを確認」するまで反映できない（取り違え防止）。
- 入力済みの値は、上書きを選んだ時だけ変える。セグメントは既に登録済みなら変えない。
- 承認の直前に、企業IDと戦略IDが取得時と同じかを確認する。違えば反映しない。

### 10.7 処理の流れ（進行の表示つき）

- 依頼（チャット：「〇〇の基本情報を入力して」）→ 会社の特定（コードリスト）→ 決算期ごとの報告書（1期ずつ呼び出し、進行を「○年○月期の有価証券報告書を確認しています」と表示）→ 候補の作成。
- AI（ask-ceo-agent）は呼ばない。チャットは候補ができたことと、承認欄の場所を示す。承認は承認欄で行う（承認するまで入力欄は変わらない）。
- 入口は2つ（`/api/stage1/autofill/identify`、`/api/stage1/autofill/report`）。停止設定（`NEXT_PUBLIC_STAGE1_AUTOFILL_DISABLED`）は両方で503を返す。認証・役割（manager以上）・戦略と会社の対応は共通の確認を通す。保存はしない。監査は会社の特定の時に残す。

### 10.9 画面の一気通貫（モックによる実ブラウザ確認）

- 依頼 → 進行表示 → 候補 → 承認 → 入力欄の反映を、ブラウザで確認（EDINETの応答は、実データから作った試験用の応答をブラウザ側で返す）。
  - チャット：「日本製罐の基本情報を入力して」→ 進行の表示（「取得中：…」）→ 候補の完了メッセージ。AI（ask-ceo-agent）への問い合わせは0回。
  - 承認欄：登録中の企業（株式会社ジャーナル）と取得対象（日本製罐）が違うため、確認のチェックを入れるまで反映できないことを確認 → 確認後、会社名を上書き → 承認 → 入力欄に「日本製罐株式会社」が入り、「反映：会社名、証券コード、上場区分、事業内容 財務：2026年度」と表示。
  - 本番の保存（データベースへの書き込み）は、ブラウザ側で送信を止めた（自動保存が本番に書き込まないように）。
- 停止設定：サーバー側の停止（503）は、両方の入口の試験で確認。

### 10.10 残課題と制限

1. 業種は、EDINETの業種名からの対応（粗い分類）。より細かい業種区分は別途。
2. セグメント名は、説明文の並びからの対応付け（件数が一致した時のみ）。名前の取り違えの可能性は、承認欄で確認する前提。
3. 従業員数は、書類の要素だけでは連結・単体を確定できない（未確認として示す）。
4. 上場市場（例：東京証券取引所プライム市場）は、候補に含めない（入力欄に該当項目がないため）。
5. 決算期の変更（月日が変わる）は、注意に残すのみで、年度の対応は確認が必要。
6. 過去の訂正は、各報告書の提出後45日の範囲のみ確認する。
7. 実データの確認は、日本製罐・丹青社の2社、各3期。他の業種・会社では、業種の対応・セグメント名の対応の精度を別途確認する。
8. 画面の一気通貫は、モックの応答で確認。実際のEDINETに対する本番の一連の操作は、検証用の環境で確認する（監査ログが本番に書き込まれるため）。

### 10.11 承認欄の改修と保存（PHASE 5D）

- 「未保存の変更あり」の原因：承認は入力欄の値を変えるだけで、保存は1.2秒後の自動保存に任せていた。自動保存の完了を確認せず完了と表示していたため、保存までの間、または保存が止まった時に未保存のまま残った。
- 承認は「承認して反映・保存」1回で、反映の後に既存の保存処理（saveStrategyData）を呼ぶ。保存が `ok: true` だったときだけ完了と表示し、チャットへ結果（反映・残した・未取得）を送る。保存できなかった時は、その旨と全体保存の案内を出す。
- ほかに未保存の変更がある時は、無関係なデータまで保存しないよう反映しない（全体保存を案内）。
- 表示：未入力は一括反映、登録済みと同じ項目は変えない、差異のある行だけ「上書き」を出す。財務は百万円の5期表（内部の値・単位は変更しない）。出典・注意は折りたたむ。
- 実ブラウザ（モックの応答）で確認：承認→保存（書き込み1回）→サイドバー「保存済み」→チャットに報告。
