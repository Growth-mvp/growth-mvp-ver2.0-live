# GROWTH 実装事実監査 要約 v1

## 1. 調査の目的

GROWTH システムの現行実装について、**特許出願に向けた進歩性検討の前提として、実装事実を整理する**ことが目的。本レポートは：

- **評価ではなく事実整理**：「進歩性がある」「似ている」などの判断はしない
- **コード確認に基づく**：推測なし、不明な点は「不明」と明記
- **特許検討資料**：下流の特許分析シート作成時に参照可能な形式で記載

## 2. 全体結論（箇条書き）

### STAGE1〜STAGE6 の処理連結の状況
- ✅ **5段階フロー実装**：STAGE1（企業価値分析）→ STAGE2（ストーリー化）→ STAGE3（カスケード）→ STAGE4（整合確認）→ STAGE6（シミュレーション）
- ✅ **識別子連結**：`strategy_id`, `department_id`, `project_id`, `okr_id` により各ステージ間でデータ紐付け
- ⚠️ **STAGE5 未実装**：`/api/stage5/execution-summary` エンドポイントは存在するが、専用ページなし
- ❌ **下流→上流の自動反映なし**：STAGE6 の計算結果が STAGE1-4 の修正判断に自動還流しない

### AI生成処理の状況
- ✅ **15エンドポイント実装**：OpenAI `gpt-4o`, `gpt-4o-turbo`, `gpt-4o-mini` 統合
- ✅ **段階的生成**：STAGE2 ドラフト → 最終ストーリー → STAGE3 カスケード → 部門別支援
- ✅ **品質維持機構**：2ndpass 修復、North Star 整合チェック、ヒント生成の段階的支援
- ❌ **エラーハンドリング明記なし**：生成失敗時のカスケード中止判定実装不明

### 永続化構造の状況
- ✅ **3層構成**：Supabase（RDB） + Zustand（メモリキャッシュ） + localStorage（クライアント一時保存）
- ✅ **自動保存**：全ステージで `useAutoSave` hook (debounce 1200ms) 対応
- ✅ **監査ログ**：`saveWithAudit()` で caller, trigger, revision 記録
- ⚠️ **テーブル確定未**：`progressLogs`, `audit_logs` 等のテーブル定義が確定していない

### 権限管理の状況
- ✅ **RBAC実装**：admin/manager/member 3段階、Capabilities マトリックス定義
- ✅ **APIガード**：`rbacGuard.ts` で全エンドポイント権限チェック
- ✅ **RLS自動適用**：Supabase RLS policy で `company_id` 単位のアクセス制御
- ✅ **権限変更即座適用**：次回 API 呼び出しで新権限で再検証

### 競合制御の状況
- ✅ **楽観ロック実装**：`revision` フィールドで DB バージョン管理
- ✅ **競合復旧機構**：API 409 時に `conflictCooldownUntil` による自動リトライ
- ✅ **ユーザー通知**：SaveStatusIndicator で保存状態可視化

### 下流→上流の自動還流の有無
- ❌ **未実装**：STAGE6 の `northStarRows`（達成率）、`simulationResult`（3年予測）、`projectContributions`（貢献度）がいずれも上流に自動フィードバックしない
- ⚠️ **手動判断ベース**：ユーザーが STAGE6 ダッシュボードを見て、必要に応じて上流ページで手動修正

### 現時点での未確認点
- **progressLogs テーブル確定未**：DB 保存先テーブル名が不明
- **answers2（部門別QA）の永続化**：DepartmentQuestionStepper からの保存実装が不明
- **stage4Plans の DB 連携**：`strategyStore` との保存連携方式が不明
- **Realtime subscription**：複数ユーザー同時編集時の自動反映有無不明
- **20項目**の詳細確認事項（詳細版参照）

## 4. 重要な実装事実

1. **3層永続化構造**
   - Supabase RDB ← Zustand メモリ ← localStorage クライアント
   - `useAutoSave` hook により全ステージで debounce (1200ms) 自動保存対応

2. **識別子ベースのデータ連結**
   - `strategy_id` → `department_id` → `project_id` → `okr_id` で全段階を紐付け
   - RLS policy で `company_id` 単位のアクセス制御

3. **AI生成 + 品質維持機構**
   - 15エンドポイントで段階的生成（ドラフト → 最終 → カスケード）
   - 2ndpass 修復、North Star 整合チェック実装

4. **楽観ロック + 競合復旧**
   - `revision` フィールドで DB バージョン管理
   - `conflictCooldownUntil` による自動リトライ

5. **下流結果の上流還流はなし**
   - STAGE6 計算結果（達成率、予測、貢献度）が上流に自動反映されない
   - ユーザー手動修正が前提

## 5. 特許検討のために重要な観察点

### データフロー構造の観察
- **一方向の識別子伝播**：上流から下流へ `strategy_id` 経由でデータが流れ、各段階で `department_id`, `project_id` 等が拡張生成される
- **完全な紐付け**：全データが UUID ベースで識別・参照可能、スコープ追跡が可能

### 生成物の段階的受け渡し
- **ドラフト → 最終版**：STAGE2 で初期ドラフト生成後、ユーザーQ&A回答を入力として最終版を再生成
- **カスケード生成**：全社戦略から部門別戦略・OKR・プロジェクトを階段的に生成・拡張
- **段階的支援**：ヒント、アドバイス、インサイトを生成で多段的に提供

### 下流結果の自動還流の制限
- **現状の限定性**：STAGE6 計算結果が STAGE1-4 に自動還流しない
- **将来の拡張可能性**：還流機構そのものはコード上実装されておらず、「自動反映なし」が設計か制約か不明

### 実装上の重要な選択肢
- **楽観ロック vs 完全分離**：revision 管理により競合検出・復旧が可能（実装済み）
- **3層構成の意図**：Supabase は永続化、Zustand はUI高速化、localStorage はクライアント一時保存で層別責務
- **RBAC の粒度**：admin/manager/member の3段階で機能制御（より細粒度な control なし）
